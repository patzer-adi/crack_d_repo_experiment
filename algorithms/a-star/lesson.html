Algorithm Lesson

A* Algorithm

Graph Algorithms Tier 2 · core O(E log V) time · O(V) space

Before you code

Clarifying questions to ask first

Ask these before writing anything. The second one is the only thing standing between A* and a wrong answer.

What does one move cost?
One step, in four directions.
→ g is a plain step count, so the answer is comparable to BFS
Which guess is safe to use?
Manhattan distance to the goal.
→ it can never over-estimate on a 4-way unit-cost grid, which is what keeps A* correct
Is the goal always reachable?
No — walls can seal it off.
→ return -1 when the open set empties without reaching it
Do we need the route or the length?
The length.
→ return g at the goal; a parent map would rebuild the route

The Insight

Add a guess of what is left, and the search stops walking backwards

Dijkstra spreads evenly in every direction because it only knows what a route has already cost. A* also asks how far there is still to go, and sorts the frontier by the sum. If that guess never over-estimates, the answer stays exactly right — but the effort goes toward the goal instead of behind it.

wall expanding now open (f = g + h) expanded goal
Why an optimistic guess keeps the answer exact:
1
f is a lower bound on the whole route
g is what a route to this cell really cost. h is a guess of the rest that is never too big. So f = g + h can never exceed the true cost of the best route through this cell — it can only be too small.
2
At the goal, the guess is zero
h(goal) = 0, so when the goal comes off the queue its f is exactly its g — a real cost, not an estimate. Nothing about it is optimistic any more.
3
So nothing left behind can beat it
Every other cell still on the queue has an f at least as large, and its f under-states the true cost of finishing through it. So no unexplored route can come in cheaper. Over-estimate anywhere and this collapses: A* would return a longer path and never notice.

The kernel

Run Dijkstra, but order the frontier by f = g + h where h never over-estimates the remaining cost. Since h is 0 at the goal, popping the goal yields its true cost, and every cell still queued has an f that under-states its route — so none can beat it. With h = 0 this is exactly Dijkstra.

Step 1

Brute force — feel the cost

The uninformed version is plain breadth-first search: expand in rings, ignoring where the goal is. It gets the same answer — but it works outward in every direction, including straight away from the target. Count the cells it expands, then compare with the A* run above.

cells expanded: 0 ring: 0

Cost: same O(E) bound, far more work in practice

BFS is not asymptotically worse — that is the point. A* wins on the constant, by never spending a pop on a cell whose optimistic total already exceeds a route it has in hand.

// Uninformed BFS: correct, but expands in every direction equally.
int bfs(vector<vector<int>>& grid, Point s, Point t) {
    queue<pair<Point,int>> q;
    q.push({s, 0}); seen[s.r][s.c] = true;
    while (!q.empty()) {
        auto [u, d] = q.front(); q.pop();
        if (u == t) { return d; }
        for (Point v : neighbours(u)) {
            if (blocked(v) || seen[v.r][v.c]) { continue; }
            seen[v.r][v.c] = true;
            q.push({v, d + 1});
        }
    }
    return -1;
}

Step 2

Translations — every optimisation, named

Three swaps turn an even spread into a directed one, without giving up the guarantee.

1
Order by cost so far → order by g + h
Give the frontier a sense of direction. A cell that is cheap to reach but points away from the goal now sorts behind one that is slightly dearer but closer.
same answer, far fewer expansions
2
Any guess → a guess that never over-estimates
This is the whole correctness condition, and it is the one people break. Manhattan distance works for 4-way unit steps because a single step changes it by exactly 1, so it can never be too big.
turns a heuristic into a guarantee
3
Decrease-key → push a duplicate, skip stale pops
Exactly as in Dijkstra: on improvement push a fresh entry, and discard any pop whose g no longer matches the stored g.
a plain heap suffices

Step 3

The algorithm in plain English

1
Set up. g[start] = 0. Push (h(start), 0, start) onto a min-heap ordered by f.
2
Pop the smallest f. If it is the goal, return its g — that is the shortest length, and you can stop immediately.
3
Drop stale entries. If the popped g is worse than the stored g for that cell, this is an old copy — skip it.
4
Relax the four neighbours. If g + 1 improves a neighbour, store it and push (g + 1 + h(v), g + 1, v).
5
If the heap empties without reaching the goal, no route exists — return -1.

Step 4

Code

C++ first — that is the version the walkthrough below animates. Delete the h term and you have Dijkstra; the rest of the code is identical.

int h(Point a, Point b) { return abs(a.r - b.r) + abs(a.c - b.c); }

int astar(vector<vector<int>>& grid, Point s, Point t) {
    int R = grid.size(), C = grid[0].size();
    vector<vector<int>> g(R, vector<int>(C, INT_MAX));
    priority_queue<Node, vector<Node>, greater<>> open;   // keyed on f
    g[s.r][s.c] = 0;
    open.push({h(s, t), 0, s});
    while (!open.empty()) {
        auto [f, gu, u] = open.top(); open.pop();
        if (u == t) { return gu; }              // h(t)=0, so gu is exact
        if (gu > g[u.r][u.c]) { continue; }        // stale copy
        for (Point v : neighbours(u)) {
            if (blocked(grid, v)) { continue; }
            if (gu + 1 < g[v.r][v.c]) {
                g[v.r][v.c] = gu + 1;
                open.push({gu + 1 + h(v, t), gu + 1, v});
            }
        }
    }
    return -1;
}
import heapq

def astar(grid, s, t):
    R, C = len(grid), len(grid[0])
    h = lambda p: abs(p[0] - t[0]) + abs(p[1] - t[1])
    g = {s: 0}
    open_ = [(h(s), 0, s)]
    while open_:
        f, gu, u = heapq.heappop(open_)
        if u == t:
            return gu
        if gu > g.get(u, float('inf')):
            continue
        r, c = u
        for dr, dc in ((1, 0), (-1, 0), (0, 1), (0, -1)):
            v = (r + dr, c + dc)
            if not (0 <= v[0] < R and 0 <= v[1] < C) or grid[v[0]][v[1]]:
                continue
            if gu + 1 < g.get(v, float('inf')):
                g[v] = gu + 1
                heapq.heappush(open_, (gu + 1 + h(v), gu + 1, v))
    return -1

Step 7

Corner cases

1
A heuristic that over-estimates
The one failure that matters. A* returns a route that is too long and reports it confidently. Using Euclidean distance with 4-way moves is fine (it under-estimates), but using Manhattan with diagonal moves allowed is not — one diagonal step cuts Manhattan by 2.
2
Returning when the goal is pushed, not popped
Tempting and wrong. When the goal is first pushed its g is only a candidate; a cheaper route may still be sitting in the heap. The guarantee applies at the moment it is popped.
3
Start or goal on a wall
Check both before the loop. Starting on a wall otherwise produces a route that walks out of one, and a walled goal is never popped so it falls through to -1 anyway — but by luck rather than design.
4
Start equals goal
Answer 0. The code above handles it: the start is popped first and matches the goal test immediately.
5
A tie between two f values
Harmless for correctness — the length is the same either way. It does change which route is found, so a test that pins the exact route rather than its length will be flaky.

Step 8

Production readiness

✓
Prove the heuristic never over-estimates for your move set, in a comment. This is the assumption that silently breaks when someone later adds diagonal movement.
✓
Return on pop, not on push. The optimality argument only holds at the pop.
✓
Keep the stale-pop guard, exactly as in Dijkstra, so a plain heap is enough.
✓
Validate start and goal before the loop — in bounds and not on a wall.
✓
If you need a route, store parents during relaxation. Re-running the search to recover it doubles the cost.
✓
Fall back to Dijkstra (h = 0) when in doubt. Slower is much better than confidently wrong, and it is a one-line change.

Step 9

Approaches — trade-offs

O(E log V)O(V)

The version above. Worth it when you have one specific goal and a cheap, honest estimate of the distance to it — maps, grids, puzzle state spaces. With no useful heuristic it degrades exactly to Dijkstra, so it is never worse than the fallback.

O(b^(d/2))O(b^(d/2))

Search from both ends and stop when the frontiers touch. On a huge branching state space this is the bigger win, because two half-depth searches are vastly smaller than one full-depth search — and it needs no heuristic at all. The catch is that you need to be able to walk edges backwards.

// expand whichever frontier is smaller, then swap
while (!a.empty() && !b.empty()) {
    if (a.size() > b.size()) { swap(a, b); }
    // expand one ring of `a`; if a cell is already in `b`, the
    // two searches have met and the answer is depthA + depthB
}
O(E) / O(E log V)O(V)

No heuristic at all. Use BFS when every move costs 1 — it is simpler and has no heap. Use Dijkstra when moves have different costs but you have no distance estimate. Both give the same length as A*; they just look at more of the map to get it.

Step 10

Complexity

Time
O(E log V)
Identical to Dijkstra in the worst case — an adversarial grid makes A* expand everything. The heuristic changes the constant, never the bound; the payoff is measured in cells expanded, not in big-O.
Space
O(V)
One g value per cell, plus a heap that can hold one entry per improvement — O(E) in the worst case, since improvements push duplicates instead of decreasing a key.

Take home

LeetCode problems that are this algorithm

LC 1091 — Shortest Path in Binary Matrix: the canonical A* fit. Moves are 8-way, so the admissible guess is Chebyshev distance (max(|dr|,|dc|)), not Manhattan.

LC 752 — Open the Lock: the graph is implicit — nodes are 4-digit states. A useful guess is the per-wheel dial distance to the target.

LC 773 — Sliding Puzzle: the classic. The sum of each tile's Manhattan distance from home never over-estimates, because one move relocates one tile by one square.

LC 787 — Cheapest Flights Within K Stops: a good counter-example — with no honest distance estimate available, plain Dijkstra or Bellman-Ford is the right call.

The trick to carry: A* is Dijkstra plus one term. All the work is in finding a guess you can prove is never too big — if you cannot, set h = 0 and you still have a correct algorithm.
