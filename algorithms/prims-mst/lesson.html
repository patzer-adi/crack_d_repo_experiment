Prim's Algorithm

Graph Algorithms Tier 2 · core O(E log V) time · O(V) space

Before you code

Clarifying questions to ask first

Ask these before writing anything. One of them decides the implementation, not the algorithm.

Is the graph connected?
Not necessarily.
→ if the blob stops growing before it holds all V nodes, no spanning tree exists
Undirected?
Yes.
→ a minimum spanning tree is only defined on undirected graphs
Dense or sparse?
Ask — it changes the code, not the idea.
→ heap for sparse graphs, a plain O(V²) scan when E approaches V²
Does the starting node matter?
No.
→ every start gives the same total weight, so node 0 is fine

The Insight

Grow one blob, always by its cheapest exit

Hold one connected group and repeatedly swallow the cheapest edge that leads out of it. That edge is the cheapest one crossing the boundary between what you have and what you do not, and such an edge always belongs to some minimum tree. So the blob is a piece of a correct answer at every moment, and never needs revising.

outside the blob reachable — a candidate exit absorbed this step in the blob
Why the cheapest exit is always safe:
1
The blob defines a cut
Everything is either in the blob or outside it. A spanning tree must connect the two sides, so at least one of its edges crosses that boundary.
2
Swapping in the cheapest crossing edge never costs more
If a minimum tree crosses by a dearer edge, remove it and add the cheapest crossing one. The result still spans and costs no more, so some minimum tree contains the cheapest exit.
3
So the blob is never wrong
It starts as a single node, which is trivially part of a minimum tree, and every absorption keeps that true. This is why there is no backtracking and no comparison of alternatives — only the current cheapest exit ever matters.

The kernel

Keep one connected blob and absorb the cheapest edge leaving it, over and over. That edge is the cheapest crossing the blob's cut, which the exchange argument places in some minimum tree — so the blob stays a subtree of a correct answer throughout. If it stalls before holding all V nodes, the graph was disconnected.

Step 1

Brute force — feel the cost

The idea works without a heap: each round, scan the entire edge list to find the cheapest edge with one end inside the blob and one end outside. Same answer, but every round re-reads every edge, including all the ones now buried deep inside the blob. Watch the scan counter.

rounds: 0 edge scans: 0 total: 0

Cost: O(V·E) time

V-1 absorptions, each preceded by a full E-edge scan. Nothing is remembered between rounds, so the same interior edges are re-examined every single time.

// Rescan every edge each round to find the cheapest exit.
for (int round = 1; round < n; round++) {
    int bw = INT_MAX, bv = -1;
    for (auto& [u, v, w] : edges) {          // full scan, every round
        if (inTree[u] && !inTree[v] && w < bw) { bw = w; bv = v; }
        if (inTree[v] && !inTree[u] && w < bw) { bw = w; bv = u; }
    }
    if (bv < 0) { return -1; }               // stalled => disconnected
    inTree[bv] = true;
    total += bw;
}

Step 2

Translations — every optimisation, named

Three swaps turn the rescan into a heap-driven single pass.

1
Rescan all edges → keep the exits in a heap
Only edges from newly absorbed nodes can be new exits. Push those once and let the heap hand back the cheapest, instead of re-deriving it from scratch each round.
O(V·E) → O(E log V)
2
Remove edges that stop being exits → skip them on pop
An edge whose far end has since been absorbed is stale, but deleting from a heap is awkward. Leave it in and test inTree[u] when it comes out.
a plain heap, no decrease-key
3
Separate connectivity check → count absorptions
The heap empties early when nothing else can be reached. Compare the count with V and the disconnected case answers itself.
no extra traversal

Step 3

The algorithm in plain English

1
Seed the heap with (0, start) — it costs nothing to absorb the starting node itself.
2
Pop the cheapest pair (w, u). If u is already in the blob this is a stale candidate — skip it.
3
Absorb u. Mark it, add w to the total, and increment the count.
4
Offer its edges. Push (weight, v) for every neighbour v not yet in the blob — these are the new candidate exits.
5
When the heap empties, return the total if all n nodes were absorbed; otherwise the graph was disconnected.

Step 4

Code

C++ first — that is the version the walkthrough below animates. It is almost exactly Dijkstra; the one change is that the heap key is the edge weight, not the total distance from the start.

long long prim(int n, vector<vector<pair<int,int>>>& adj) {
    vector<bool> inTree(n, false);
    priority_queue<pair<int,int>,
                   vector<pair<int,int>>, greater<>> pq;
    pq.push({0, 0});                // (edge weight, node)
    long long total = 0;
    int used = 0;
    while (!pq.empty()) {
        auto [w, u] = pq.top(); pq.pop();
        if (inTree[u]) { continue; }     // stale exit
        inTree[u] = true;
        total += w;
        used++;
        for (auto& [v, wt] : adj[u]) {
            if (!inTree[v]) { pq.push({wt, v}); }
        }
    }
    return used == n ? total : -1;    // -1 = disconnected
}
import heapq

def prim(n, adj):
    in_tree = [False] * n
    pq = [(0, 0)]
    total, used = 0, 0
    while pq:
        w, u = heapq.heappop(pq)
        if in_tree[u]:
            continue
        in_tree[u] = True
        total += w
        used += 1
        for v, wt in adj[u]:
            if not in_tree[v]:
                heapq.heappush(pq, (wt, v))
    return total if used == n else None

Step 7

Corner cases

1
A disconnected graph
The heap runs dry with used < n. Returning the total anyway reports the weight of one component's tree, which is not a spanning tree of the graph. Check the count.
2
Forgetting the stale-pop test
Without if (inTree[u]) continue; a node is absorbed once per queued candidate, so its weight is added several times and used overshoots n. The answer comes out too large.
3
Seeding with weight 0
Deliberate, not a hack. The start node joins the blob for free because no edge is used to reach it, so pushing (0, start) keeps the loop uniform and adds nothing to the total.
4
Keying the heap on total distance
That is Dijkstra, not Prim, and it gives a shortest-path tree instead of a minimum spanning tree — often a different tree with a larger total. The key must be the single edge's weight.
5
A dense graph
With E ≈ V² the heap holds V² entries and O(E log V) is worse than a plain O(V²) scan for the cheapest exit. Same algorithm, different data structure.

Step 8

Production readiness

✓
Check used == n before returning. That single comparison is the disconnected-graph guard.
✓
Keep the stale-pop test. It replaces decrease-key and is the only thing stopping double-counting.
✓
Key the heap on the edge weight, never on a running total. That one character is the whole difference from Dijkstra.
✓
Accumulate into 64-bit. V-1 large weights overflow a 32-bit total.
✓
Pick the implementation from the density. Heap for sparse, O(V²) scan for dense — a factor of log V either way.
✓
For the edges themselves, push (weight, node, from) and record from on each absorption. No second pass needed.

Step 9

Approaches — trade-offs

O(E log V)O(V)

The version above. The default when the graph is sparse and you already hold an adjacency list. It also stops early in a natural way if you only want the first k absorptions.

O(V²)O(V)

Keep best[v] = the cheapest known edge into v, and each round scan the array for the smallest among nodes outside the blob. No heap, no stale entries, and on a dense graph it beats the heap version — sorting or heaping V² edges costs more than V² scanning does.

vector<int> best(n, INT_MAX); best[0] = 0;
for (int it = 0; it < n; it++) {
    int u = -1;
    for (int v = 0; v < n; v++) {           // scan, no heap
        if (!inTree[v] && (u < 0 || best[v] < best[u])) { u = v; }
    }
    if (best[u] == INT_MAX) { return -1; }   // disconnected
    inTree[u] = true; total += best[u];
    for (int v = 0; v < n; v++) { best[v] = min(best[v], w[u][v]); }
}
O(E log E)O(V)

Same problem, opposite strategy: sort every edge and merge many components instead of growing one. Prefer it when the input arrives as an edge list, or when you need union-find anyway. Prefer Prim when the graph is dense or already an adjacency list.

Step 10

Complexity

Time
O(E log V)
Each edge is pushed at most twice — once when each endpoint is absorbed — so the heap sees O(E) entries, each pushed and popped at O(log V). The stale-pop test is O(1).
Space
O(V)
One flag per node. The heap itself can reach O(E) entries, because stale candidates are left in rather than removed.

Take home

LeetCode problems that are this algorithm

LC 1584 — Min Cost to Connect All Points: the graph is complete, so E = V². This is the one where dense Prim genuinely beats Kruskal — no V² edge list to build or sort.

LC 1135 — Connecting Cities With Minimum Cost: sparse and given as an edge list, so either works; the disconnected check is the real content.

LC 1168 — Optimize Water Distribution in a Village: the trick is a virtual node 0 with the well costs as its edges. After that it is one unchanged MST run.

The trick to carry: Prim is Dijkstra with the heap keyed on the edge weight instead of the running total. If you can write one, you can write the other — just be sure which one the problem wants.
