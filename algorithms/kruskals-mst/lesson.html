Algorithm Lesson

Kruskal's Algorithm

Graph Algorithms Tier 2 · core O(E log E) time · O(V) space

Before you code

Clarifying questions to ask first

Ask these before writing anything. The first one decides whether an answer exists.

Is the graph connected?
Not necessarily.
→ then no spanning tree exists. Say so, rather than returning the weight of a forest.
Undirected?
Yes.
→ a minimum spanning tree is only defined on undirected graphs. The directed analogue is a different algorithm entirely.
Can two edges share a weight?
Yes.
→ the tree is then not unique, but its total weight is — so the answer is still well defined
Total weight, or the edges themselves?
The total.
→ the edge list falls out of the same loop if a caller wants it

The Insight

Take the cheapest edge that joins two things not yet joined

Sort the edges and walk them cheapest first. Accept an edge unless both its ends already sit in the same group — that one would close a cycle, and the priciest edge of any cycle is always removable. So the only question per edge is "are these two already connected?", and the answer builds itself.

node (label = its group) edge under consideration accepted into the tree rejected — would close a cycle
Why greed is safe here:
1
Split the nodes any way you like
Take any way of cutting the nodes into two halves. A spanning tree has to connect them, so at least one of its edges crosses that cut.
2
The cheapest edge across the cut is always safe
Suppose a minimum tree uses a dearer crossing edge instead. Swap it for the cheapest one: the result still spans, and it costs no more. So some minimum tree contains the cheapest crossing edge.
3
Every edge Kruskal accepts is such an edge
When an edge joins two different groups, cut the nodes along that group's boundary. Every cheaper edge was already examined and either accepted or found to be inside a group, so this is the cheapest one crossing. Safe, every time.

The kernel

Sort the edges and accept each one whose endpoints are in different groups, merging the groups as you go. Every accepted edge is the cheapest crossing some cut, which the exchange argument shows belongs to a minimum tree. After V-1 acceptances the tree is complete; fewer means the graph was never connected.

Step 1

Brute force — feel the cost

Without the greedy argument you would have to check candidates: pick every set of V-1 edges, test whether it connects everything without a cycle, and keep the cheapest that does. It is correct and completely impractical — the number of subsets explodes. Watch the counter.

subsets tried: 0 valid trees found: 0 best so far: —

Cost: C(E, V-1) subsets — exponential

Seven edges and five nodes already means 35 subsets, and it grows fast from there. Worse, nearly all of them are invalid, so almost all the work is wasted on candidates that were never trees.

// Try every subset of V-1 edges; keep the cheapest that spans acyclically.
long long best = INF;
for (int mask = 0; mask < (1 << E); mask++) {
    if (popcount(mask) != n - 1) { continue; }
    if (!spansWithoutCycle(mask)) { continue; }   // a full check, each time
    best = min(best, weightOf(mask));
}

Step 2

Translations — every optimisation, named

Three swaps take subset search down to one sort and one sweep.

1
Search all subsets → sort once and be greedy
The cut property says the cheapest edge across any split is safe, so no search is needed. Look at each edge once, in weight order, and decide on the spot.
exponential → O(E log E)
2
Detect cycles by traversal → union-find
"Would this edge close a cycle?" is just "are these two already in the same group?". Union-find answers it in near-constant time instead of a fresh O(V) search per edge.
O(V) per edge → O(α(V)) per edge
3
Separate connectivity test → count acceptances
A spanning tree has exactly V-1 edges. If the sweep ends with fewer, the graph was in pieces — no extra pass needed to find that out.
the disconnected case for free

Step 3

The algorithm in plain English

1
Sort every edge by weight, cheapest first. This is the only ordering the algorithm ever needs.
2
Put each node in its own group. At the start nothing is connected to anything.
3
Walk the edges in order. Ask whether the two ends are already in the same group.
4
Same group → skip it. Both ends are already connected, so this edge would only close a cycle.
5
Different groups → take it. Merge the two groups and add the weight. Stop at n-1 accepted edges; ending with fewer means the graph was disconnected.

Step 4

Code

C++ first — that is the version the walkthrough below animates. The union-find is the whole trick; without it this is O(V·E).

int find(vector<int>& p, int x) {
    while (p[x] != x) { p[x] = p[p[x]]; x = p[x]; }   // path compression
    return x;
}

long long kruskal(int n, vector<array<int,3>> edges) {
    sort(edges.begin(), edges.end(),
         [](auto& a, auto& b) { return a[2] < b[2]; });
    vector<int> p(n);
    for (int i = 0; i < n; i++) { p[i] = i; }
    long long total = 0;
    int used = 0;
    for (auto& [u, v, w] : edges) {
        int ru = find(p, u), rv = find(p, v);
        if (ru == rv) { continue; }              // would close a cycle
        p[ru] = rv;
        total += w;
        if (++used == n - 1) { break; }
    }
    return used == n - 1 ? total : -1;            // -1 = disconnected
}
def kruskal(n, edges):
    p = list(range(n))

    def find(x):
        while p[x] != x:
            p[x] = p[p[x]]
            x = p[x]
        return x

    total, used = 0, 0
    for u, v, w in sorted(edges, key=lambda e: e[2]):
        ru, rv = find(u), find(v)
        if ru == rv:
            continue
        p[ru] = rv
        total += w
        used += 1
        if used == n - 1:
            break
    return total if used == n - 1 else None

Step 7

Corner cases

1
A disconnected graph
The sweep finishes with fewer than V-1 accepted edges. Returning the total anyway silently reports the weight of a spanning forest, which is a different object. Check the count and say so.
2
Comparing nodes instead of roots
The classic bug: writing if (u == v) instead of if (find(u) == find(v)). It only catches self-loops, so cycles slip in and the "tree" ends up with too many edges.
3
Union-find without compression or union by size
Still correct, but the chains can grow to length V and each find becomes O(V) — turning the sweep into O(V·E) and quietly undoing the whole point.
4
Equal weights
Ties change which tree comes out but never its total. If a test pins the exact edge list it will be flaky; pin the weight instead.
5
A single node
V-1 is 0, so zero edges are needed and the answer is 0. The loop never accepts anything and the count check passes — but only if you write used == n - 1 rather than used > 0.

Step 8

Production readiness

✓
Check used == n - 1 before returning. This is the disconnected-graph guard and it costs nothing.
✓
Compare roots, never node ids. find(u) == find(v) is the cycle test; anything else lets cycles through.
✓
Use path compression and union by size. Both are two lines and together they make find effectively constant.
✓
Accumulate into 64-bit. V-1 edges of large weight overflow a 32-bit total well before the graph gets big.
✓
Break at n-1 acceptances. Once the tree is complete the remaining edges cannot change anything.
✓
Sort by weight only. Sorting the whole triple compares node ids on ties, which is harmless but obscures that the tie-break is arbitrary.

Step 9

Approaches — trade-offs

O(E log E)O(V)

The version above. Best on sparse graphs and when the edges arrive as a list — which is how most problems hand them to you. It also tells you the graph is disconnected for free, and the union-find it needs is reusable elsewhere in the same problem.

O(E log V)O(V)

Grow one blob instead of merging many: repeatedly absorb the cheapest edge leaving the tree, using a heap. Better on dense graphs — with an adjacency matrix and a plain scan it runs in O(V²), beating a sort of V² edges. Also the natural choice when you already hold an adjacency list.

pq.push({0, 0});                       // (weight, node)
while (!pq.empty() && used < n) {
    auto [w, u] = pq.top(); pq.pop();
    if (inTree[u]) { continue; }
    inTree[u] = true; total += w; used++;
    for (auto& [v, wt] : adj[u]) {
        if (!inTree[v]) { pq.push({wt, v}); }
    }
}
O(E log V)O(V)

Every component picks its own cheapest outgoing edge, all at once, and they all merge. The component count at least halves each round, so O(log V) rounds suffice. Rarely the best choice on one machine, but it is the one that parallelises — each component's choice is independent.

Step 10

Complexity

Time
O(E log E)
The sort dominates. The sweep itself does two find calls per edge at O(α(V)) each — effectively constant — so it contributes only O(E). Since log E ≤ 2 log V, this is often written O(E log V).
Space
O(V)
The parent and size arrays, one entry per node. The edge list is the input; sorting it in place adds nothing.

Take home

LeetCode problems that are this algorithm

LC 1584 — Min Cost to Connect All Points: build the complete edge list from the Manhattan distances, then run this code unchanged. The only decision is Kruskal on V² edges versus dense Prim.

LC 1135 — Connecting Cities With Minimum Cost: Kruskal plus the disconnected check, which is the entire point of the problem.

LC 1489 — Critical and Pseudo-Critical Edges in MST: run Kruskal repeatedly — once forcing an edge in, once banning it — and compare totals. Only tractable because one run is cheap.

LC 1697 — Checking Existence of Edge Length Limited Paths: not an MST, but the same idea: sort edges and queries together, and union as you sweep.

The trick to carry: "connect everything as cheaply as possible" is Kruskal. And any time you sort edges and sweep, union-find is the structure that makes the sweep cheap.
