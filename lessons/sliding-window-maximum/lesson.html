Sliding Window Maximum

LC #239 Hard Sliding Window

Before you code

Clarifying questions to ask first

Ask these before writing any code. Each answer constrains a specific design choice.

How many maxima do we return?

Exactly n − k + 1 — one per window. The first window covers indices [0..k−1]; the last covers [n−k..n−1].

→ record only once i ≥ k − 1

Can elements be negative or zero?

Yes — values lie in [−10⁴, 10⁴]. So 0 is not a safe sentinel for "smaller than everything seen so far".

→ compare values directly; never use 0 or −1 as magic

Can k exceed the array length?

No — constraints guarantee 1 ≤ k ≤ n. Every window fits.

→ no bounds guard; loop ranges are always valid

Can the array contain duplicates?

Yes. If two equal values are in the same window, either one is a valid max — no tie-break needed.

→ use ≤ (not <) when evicting older candidates

Assumptions we carry forward

nums is non-empty, k is a valid window size, values may be negative. We return n − k + 1 maxima in left-to-right order. We never need to handle k > n or an empty input.

The Insight

Once a bigger value lands to your right, you're dominated forever.

For each window of size k we want a max. Brute force rescans k cells every step. Notice: when a new value v enters at index i, every smaller value sitting to its left can never beat v — every future window that contains them also contains v, so they're permanently dominated. Drop them. The set of "could still be max" indices forms a chain whose values strictly decrease left to right.

The kernel

Maintain a deque of indices whose values strictly decrease left to right. For each new index i, pop dominated entries from the back (nums[back] ≤ nums[i]), push i; then pop the front if it slid out of the window (front ≤ i − k). The front is always the current window's max. Each index is pushed and popped at most once — amortised O(1) per step, O(n) total.

Step 1

Brute force — feel the cost

For every window start i ∈ [0, n−k], walk all k elements and remember the largest. Output that max, slide one cell right, repeat. Two nested loops — O(n·k) time, O(1) extra space. With n = 10⁵ and k ≈ 10⁵, that's 10¹⁰ comparisons — comfortably TLE. Step through to see why every slide redoes work the previous slide already did.

Cost: O(n·k) time, O(1) space

Each of the n − k + 1 windows re-scans k elements from scratch. The checks counter makes it visible: when the window slides one step right, we throw away k−1 comparisons we just did. The deque solution below pays each index exactly twice — once on push, once on pop.

vector<int> maxSlidingWindow_BF(vector<int>& nums, int k) {
    int n = nums.size();
    vector<int> out;
    for (int i = 0; i <= n - k; i++) {
        int best = nums[i];
        for (int j = i + 1; j < i + k; j++) {
            if (nums[j] > best) { best = nums[j]; }
        }
        out.push_back(best);
    }
    return out;
}

Step 2

Translations — every optimisation, named

Three independent moves take us from O(n·k) to O(n). Each removes a different kind of waste: redundant re-scanning, redundant max comparison, and the cost of the data structure itself.

1
Brute force — rescan each window
For each of the n − k + 1 window starts, walk all k cells and remember the largest. Every slide throws away k−1 comparisons just done.
O(n·k) time, O(1) space
2
Max-heap with lazy deletion
Push (value, index) for every element. When reading the window max, pop entries from the top whose index ≤ i − k (expired) until the top is in-window. Heap operations cost O(log n); each element enters once.
O(n log n) time, O(n) space
3
Discard dominated values — monotonic deque
Maintain a deque of indices whose values strictly decrease left to right. When index i arrives: while nums[back] ≤ nums[i]: pop back; push i; if dq[0] ≤ i − k: popleft. Front is the current max. Each index touches the deque at most twice — O(1) amortised per step.
O(n) time, O(k) space — taught

Step 3

The algorithm in plain English

1
Create an empty deque dq. It stores indices, not values. Create an empty result list out.
2
For each index i from 0 to n−1:
3
While the deque is non-empty and nums[dq.back()] ≤ nums[i], pop from the back. (Those indices are dominated by the new value.)
4
Push i onto the back of the deque.
5
If dq.front() ≤ i − k, popleft — the front has slid out of the window.
6
If i ≥ k − 1, append nums[dq.front()] to out. Return out after the loop.

Step 4

Code

vector<int> maxSlidingWindow(vector<int>& nums, int k) {
    int n = nums.size();
    vector<int> out;
    deque<int> dq;                                 // stores indices, values strictly decreasing
    for (int i = 0; i < n; i++) {
        // 1. Pop dominated indices from the back.
        while (!dq.empty() && nums[dq.back()] <= nums[i]) {
            dq.pop_back();
        }
        // 2. Push current index.
        dq.push_back(i);
        // 3. Pop the front if it slid out of the window.
        if (dq.front() <= i - k) {
            dq.pop_front();
        }
        // 4. Record once the window is full.
        if (i >= k - 1) {
            out.push_back(nums[dq.front()]);
        }
    }
    return out;
}

Step 7

Corner cases

1
Single element [5], k=1
Loop runs once. Push idx 0; window already full at i=0 (since i ≥ k−1 = 0). Front is the only candidate. Output: [5].
2
k = 1 — output equals input
Every cell is its own window. Each iteration pushes the new index; the front-pop check dq[0] ≤ i − 1 fires every step, leaving the deque holding only the current index. Output is just nums itself.
3
k = n — single window over the whole array
Output has length 1. The front-pop branch never fires (no front index ever drops below 0). The deque ends holding whichever indices survived all back-pops, with the global max at the front.
4
Strictly decreasing [5,4,3,2,1], k=3
No back-pops ever happen — every new value is smaller than its predecessor. The deque grows to size k, then front-pops every step. Output: [5,4,3]. This is the case where the deque is at its largest.
5
Strictly increasing [1,2,3,4,5], k=3
Every new value clears the entire back of the deque. The deque never holds more than one index. Output: [3,4,5]. Front-pops never fire because the deque is already cleared down to the new index.
6
All equal [7,7,7,7], k=2
The ≤ rule pops the older equal-valued back entry on every step, so the deque stays size 1. Output: [7,7,7]. If we used strict <, the deque would accumulate stale duplicates that the front-pop would later have to clean up — same result, more work.

Step 8

Production readiness

✓
Deque stores indices, not values. Storing values forces a second container for "what's the index?" lookups. Indices give you both — the index is the position, and nums[idx] is the value.
✓
Pop with ≤, not <. Equal values to the left of a newer copy are dominated — the newer one will outlive them and is always a valid max while it's in the window.
✓
Front-pop check uses ≤ i − k, not < i − k + 1. Both are equivalent, but ≤ i − k reads as "index that just fell out of the new window starting at i − k + 1".
✓
Record only after the window is full. Guard with if (i ≥ k − 1) — record before this and the first k−1 outputs are partial-window maxes, which is wrong.
✓
Reserve output capacity. The result has length n − k + 1. In C++, out.reserve(n - k + 1) avoids repeated vector reallocation on tight loops.
✓
Use std::deque<int> or a hand-rolled ring buffer. Both are O(1) at both ends. Avoid std::list (cache-unfriendly) and avoid std::vector as a back-and-front structure (front pop is O(n)).
✓
Each index touches the deque ≤ 2 times. Once on push, at most once on pop. The total work is bounded by 2n — amortised O(1) per step, even though one iteration can pop many entries.

Step 9

Approaches — trade-offs

Time O(n·k) Space O(1)

For each window start, walk all k cells and remember the max. Simplest possible — and fine if k is tiny. TLE on the LeetCode upper bound (n = 10⁵, k ≈ 10⁵). Worth knowing because it makes the cost of redundant rescanning visible.

vector<int> maxSlidingWindow(vector<int>& nums, int k) {
    int n = nums.size();
    vector<int> out;
    for (int i = 0; i <= n - k; i++) {
        int best = nums[i];
        for (int j = i + 1; j < i + k; j++) {
            if (nums[j] > best) { best = nums[j]; }
        }
        out.push_back(best);
    }
    return out;
}
Time O(n log n) Space O(n)

Push (value, index) pairs onto a max-heap. When reading the answer, pop expired pairs (index ≤ i − k) from the top until the top is in-window. Each element enters once and may be popped once — n heap operations of cost O(log n). Cleaner when the language has no native deque, but always slower than the deque on this problem. Generalises to "k-th largest of every window" where the deque trick alone does not.

vector<int> maxSlidingWindow(vector<int>& nums, int k) {
    int n = nums.size();
    vector<int> out;
    priority_queue<pair<int, int>> heap;   // (value, index)
    for (int i = 0; i < n; i++) {
        heap.emplace(nums[i], i);
        if (i >= k - 1) {
            while (heap.top().second <= i - k) {
                heap.pop();
            }
            out.push_back(heap.top().first);
        }
    }
    return out;
}
Time O(n) Space O(k)

Maintain a deque of indices whose values strictly decrease left to right. Each new index pops dominated indices from the back, then pushes itself; an expired front is popped on entry. The front is always the window's max. Each index is touched at most twice — total work is bounded by 2n. The canonical answer. Subtler to derive, but lighter and faster than the heap.

vector<int> maxSlidingWindow(vector<int>& nums, int k) {
    int n = nums.size();
    vector<int> out;
    deque<int> dq;
    for (int i = 0; i < n; i++) {
        while (!dq.empty() && nums[dq.back()] <= nums[i]) {
            dq.pop_back();
        }
        dq.push_back(i);
        if (dq.front() <= i - k) {
            dq.pop_front();
        }
        if (i >= k - 1) {
            out.push_back(nums[dq.front()]);
        }
    }
    return out;
}

Step 10

Complexity

Time
O(n)
Each index is pushed onto the deque exactly once and popped at most once. Total deque work over the whole array is bounded by 2n, so the inner while's amortised cost per outer step is O(1).
Space
O(k)
The deque holds only indices inside the current window — at most k of them. The output of length n−k+1 is not counted (it's required output, not auxiliary memory).

Take home

Related problems that use this pattern

LC 1438 — Longest Continuous Subarray With Absolute Diff ≤ Limit. Two monotonic deques in parallel — one tracking the window max, one tracking the window min — so max − min ≤ limit is O(1) per slide. Exact same "dominated candidates" idea, applied twice.

LC 862 — Shortest Subarray with Sum at Least K. Monotonic deque on prefix sums, not raw values. Drop dominated prefix sums from the back; pop from the front when prefix[i] − prefix[front] ≥ k. Same skeleton, different invariant.

LC 84 — Largest Rectangle in Histogram. Monotonic stack (one-sided deque). Keep a stack of indices whose bar heights are non-decreasing; pop and settle rectangles whenever a shorter bar arrives. Cousin of the deque trick — front-only access.

LC 480 — Sliding Window Median. Same window structure, but the per-window question is median instead of max. Two heaps (lo max-heap, hi min-heap) with lazy deletion replace the deque — the monotonic-chain trick doesn't generalise beyond order-statistics endpoints (min / max).
