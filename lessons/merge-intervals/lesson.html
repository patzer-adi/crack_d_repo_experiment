Merge Intervals

LC #56 Medium Arrays

Before you code

Clarifying questions to ask first

These four questions decide whether the algorithm collapses to a one-pass sweep or stays an O(n²) tangle.

Are the input intervals sorted?

No — they arrive in arbitrary order.

→ we must sort first. Sorting by start key is what turns an O(n²) all-pairs overlap check into one linear sweep.

Do [1,4] and [4,7] overlap?

Yes — intervals are closed and touching counts as overlap. [1,4] ∪ [4,7] = [1,7].

→ overlap test must be next.start <= open.end with ≤, not strict <.

Can intervals be identical or fully contained?

Yes — duplicates and full containment are both allowed.

→ extend with open.end = max(open.end, next.end): the next end may be smaller (containment) or equal (duplicate).

Can the input be empty?

Per LC the constraint is n ≥ 1, but defending against empty is cheap.

→ a single early-return guard for empty input; otherwise we can safely seed the sweep with intervals[0].

Assumptions we carry forward

Closed intervals; touching counts as overlap; duplicates and containment allowed. We may freely sort the input (no stability requirement).

The Insight

Sort by start, then sweep with a single "open" interval.

Once intervals are sorted by start, overlap becomes a local condition. If next.start > open.end, then no later interval can overlap open either — every subsequent start is at least as large. So we can finalise open and move on, with no risk of missing a merge later. The sort is what makes a single linear sweep correct.

Step 1

Brute force — check every pair

Without sorting, the only safe way to merge is to compare every pair of intervals. Even worse: when two intervals merge, the result may now overlap a third interval we already passed — so we must repeat the all-pairs scan until a full pass produces no new merges. Quadratic per pass, possibly multiple passes.

intervals (one row per item)

Cost: O(n²) per scan — and possibly multiple scans

Without sorting, a merge can create a new overlap with an already-checked interval. Sort + sweep eliminates this re-checking entirely.

vector<vector<int>> mergeBF(vector<vector<int>>& iv) {
    bool changed = true;
    while (changed) {
        changed = false;
        for (int i = 0; i < (int)iv.size(); i++) {
            for (int j = i + 1; j < (int)iv.size(); j++) {
                if (iv[i][1] >= iv[j][0] && iv[j][1] >= iv[i][0]) {
                    iv[i] = { min(iv[i][0], iv[j][0]), max(iv[i][1], iv[j][1]) };
                    iv.erase(iv.begin() + j);
                    changed = true; j--;
                }
            }
        }
    }
    return iv;
}

Step 2

Four translations to O(n log n)

The brute force re-checks pairs that already had their chance to merge. These four translations replace it with a sort plus one linear sweep.

1

Translation 1 — Reduce overlap to one comparison

Two intervals [a,b] and [c,d] overlap iff a ≤ d && c ≤ b. If we know the one with the smaller start, the test reduces to a single comparison: next.start ≤ open.end.

→ a per-pair O(1) check, but only useful once we can guarantee the ordering.

2

Translation 2 — Sort by start

Sorting by start guarantees that for the interval we are currently building (open), every future interval has a start ≥ the one we are currently looking at. So if the current next interval is disjoint, every later one is disjoint too. Disjoint here means disjoint forever.

→ removes the "may have to re-scan" liability of the brute force. One pass is enough.

3

Translation 3 — Sweep with one mutable "open" interval

Carry one mutable [open.start, open.end] through the loop. On overlap, extend open.end in place; on disjoint, push open to the output and replace it with next. After the loop, push the final open.

→ O(1) state per step. No nested loops, no re-scans.

4

Translation 4 — max handles containment and duplicates

Extending with open.end = max(open.end, next.end) covers the cases where next is fully contained in open (next.end < open.end) or identical to it. No special-case branches needed.

→ a single line of arithmetic replaces three or four conditional branches.

Step 3

The algorithm in plain English

1.Sort intervals by start.
2.Initialise out = [] and open = intervals[0].
3.For each next in intervals[1..]:
4.If next.start ≤ open.end: extend — open.end = max(open.end, next.end).
5.Else: finalise — push open to out; open = next.
6.Flush the final open to out; return out.

Why the final flush is mandatory

The loop only emits open when a disjoint next is encountered. The last open interval never sees a disjoint successor — there are none — so it must be flushed explicitly after the loop ends.

Step 4

Canonical C++ solution

Try to reproduce this from the six steps before revealing.

vector<vector<int>> merge(vector<vector<int>>& intervals) {
    sort(intervals.begin(), intervals.end());
    vector<vector<int>> out;
    vector<int> open = intervals[0];
    for (int i = 1; i < (int)intervals.size(); i++) {
        int s = intervals[i][0], e = intervals[i][1];
        if (s <= open[1]) {                       // overlap: extend
            open[1] = max(open[1], e);
        } else {                                  // disjoint: finalise
            out.push_back(open);
            open = { s, e };
        }
    }
    out.push_back(open);                          // flush the final open
    return out;
}

Step 7

Corner cases

1

Single interval — [[1,2]] → [[1,2]]

The loop body never runs. We seed open = intervals[0] and the final flush emits it. Returns the input unchanged.

2

Touching at endpoint — [[1,4], [4,7]] → [[1,7]]

The overlap test must be ≤, not <. With <, touching intervals would be wrongly emitted as separate.

3

Fully contained — [[1,10], [3,5]] → [[1,10]]

Sorted as-is. 3 ≤ 10, so extend with max(10, 5) = 10. The contained interval contributes nothing new — exactly what max guarantees.

4

Identical duplicates — [[2,5], [2,5]] → [[2,5]]

Same path as containment: max(5, 5) = 5. Output has one interval.

5

No overlaps — [[1,2], [3,4], [5,6]] → unchanged

Every iteration takes the finalise branch. Output is the input (post-sort).

Step 8

Production readiness

✓

Final flush: the loop emits open only when a disjoint next arrives; the last open needs an explicit push after the loop.

✓

Closed-interval semantics: overlap test uses ≤ so touching intervals merge.

✓

Containment / duplicates: handled by max(open.end, next.end) — no special branches.

✓

Empty input: guard with an early return, or document the precondition n ≥ 1.

✓

In-place sort: we mutate the caller's array. If callers shouldn't see this, sort a copy (extra O(n) memory).

✓

Integer overflow: none — endpoints are stored, never summed.

Step 9

Approaches — trade-offs

Time O(n log n)Space O(n) (output) + O(log n) (sort stack)

Sort by start, sweep with one mutable open interval. The algorithm above. Sort dominates the time; the sweep itself is O(n).

Time O(n log n)Space O(n)

Build a graph: one node per interval, an edge between any two that overlap. Run a connected-components search; for each component, output one merged interval (its min start, max end). Same complexity as sort + sweep but with worse constants and far more code. Useful framing only when intervals are already part of a graph problem.

Time O(n²) or worseSpace O(1) extra

Repeatedly scan all pairs and merge any that overlap, until a full pass produces no change. Correct but ugly: a single merge can create a new overlap with an interval the scan already passed. Useful only as the derivation anchor for the translations above.

Take home

Related problems that use this pattern

The sort-then-sweep template: any problem where a "global" predicate (overlap, conflict, coverage) reduces to a local check after sorting. Sort makes the relevant condition local; the sweep maintains O(1) state to evaluate it.

In an interview: brute force first (all pairs), then point out that sorting by start makes overlap a local condition — once next.start > open.end, no later interval can overlap open. Then code the sweep.
