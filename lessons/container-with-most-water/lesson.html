Container With Most Water

LC #11 Medium Arrays · Two Pointers

Before you code

Clarifying questions to ask first

Ask these before writing anything. Each answer constrains the design.

What does height[i] represent?

The height of a vertical line at position i. Non-negative integers.

→ area = min(h[L], h[R]) × (R − L)

Can we use the same line twice?

No — two distinct indices i < j form a container.

→ L and R are always distinct; L starts at 0, R at n-1

Can heights be zero?

Yes — a zero-height line creates zero area with any partner.

→ no special-casing; formula handles it

What do we return?

int — the maximum area any two lines can contain.

→ track a running max, return at end

Assumptions we carry forward

n ≥ 2 (guaranteed — at least two lines always exist). Heights are non-negative integers. The container uses vertical lines only — no slanted sides. Water cannot spill over the shorter line.

The Insight

Area is capped by the shorter line — moving it inward is the only move with any upside.

Two pointers start at the outermost lines and walk inward. Area is (R − L) × min(h[L], h[R]): width × shorter wall. Moving the taller side shrinks width without raising the cap — no upside. Only moving the shorter side can let the cap rise. Sweep once, always move the shorter side, track the best.

The kernel

area = min(h[L], h[R]) × (R − L); move the shorter pointer inward; track best.
Discarded pairs are dominated; no maximum is missed.

Step 1

Brute force: check every pair

Try every pair (i, j) with i < j. Compute min(h[i], h[j]) × (j−i). Track the running maximum.

i=—  j=—  · area=—  · best=—  · checks:0

Cost: O(n²) time

C(n,2) = n(n−1)/2 pairs. For n=10⁵ that is ~5×10⁹ checks.

int maxArea_BF(vector<int>& h) {
    int best = 0, n = h.size();
    for (int i = 0; i < n - 1; i++) {
        for (int j = i + 1; j < n; j++) {
            best = max(best, min(h[i], h[j]) * (j - i));
        }
    }
    return best;
}

Step 2

One translation eliminates the inner loop

The brute force has no way to discard unpromising pairs. The greedy argument gives us exactly that — a proof that every pair involving the taller pointer at a narrower width is dominated.

1

Translation 1 — Move shorter pointer → inner loop eliminated

Start L=0, R=n−1 (widest container). At each step, record the area and move the shorter pointer inward. The greedy proof guarantees we never miss the optimal pair — once we've seen a pair, all pairs with the taller pointer at a shorter width are provably smaller (same or lower cap, less width).

h[L] < h[R] → L++ // left is cap, moving R inward can't help
h[L] > h[R] → R-- // right is cap, moving L inward can't help
h[L] == h[R] → L++ // either valid by symmetry; convention: L++

→ O(n²) → O(n). O(1) space — L, R, best, cap, width, area only.

Unlike 3Sum: no sort needed

3Sum sorts so the sign of the sum tells the pointer which direction to move. Here the decision is based on relative heights — the original positions encode the width, which sorting would destroy.

Step 3

The algorithm in plain English

Say this before writing any code.

1.Initialize L=0, R=n−1, best=0. Start at the widest container.
2.While L < R: compute cap = min(h[L], h[R]), width = R−L, area = cap × width. Update best if larger.
3.If h[L] < h[R]: L++ — left is the cap, moving R cannot improve it.
4.Else: R-- — right is cap (or equal). Both are equally limiting when equal.
5.When L ≥ R: all pairs evaluated. Return best.

Step 4

Canonical C++ solution

Try writing from the five steps above before revealing.

int maxArea(vector<int>& height) {
    int L = 0, R = (int)height.size() - 1;
    int best = 0;

    while (L < R) {
        int cap   = min(height[L], height[R]);
        int width = R - L;
        int area  = cap * width;
        if (area > best) { best = area; }

        if (height[L] < height[R]) { L++; }
        else                        { R--; }
    }
    return best;
}

Step 7

Corner cases

1

Minimum input — [1,1]

L=0, R=1. One step: cap=1, width=1, area=1. Equal heights → L++. L≥R, done. Returns 1. n≥2 guaranteed so the loop always runs at least once.

2

All same height — [5,5,5,5]

First pair (widest): area=5×3=15. Equal → L++ each step. Subsequent pairs are narrower — all smaller. Returns 15 on the very first step.

3

Monotone increasing — [1,2,3,4,5]

Outermost gives area=1×4=4 — not the best. L=1, R=4: area=2×3=6. The greedy correctly discards h=1 (the cap) first. Do not assume the outermost pair is always the answer.

4

Tall centre — [1,100,1]

L=0 h=1, R=2 h=1: area=1×2=2, equal → L++. L=1 h=100, R=2 h=1: cap=1, area=1×1=1. Returns 2. The tall centre bar is irrelevant — water spills over the short outer lines.

5

Symmetric — [4,3,2,1,4]

Equal outer heights → L++ (convention). Best is the first pair: cap=4, width=4, area=16. All subsequent pairs are smaller. The convention choice (L++ vs R--) does not affect correctness.

Step 8

Production readiness

✓

n=2: one iteration, L++ or R-- makes L≥R immediately. Correct.

✓

Area never negative: heights ≥ 0 and width = R−L ≥ 1 inside the loop.

✓

Integer overflow: max n=10⁵, max h=10⁴. Max area = 10⁹ — fits in int (2.1×10⁹). Safe.

✓

Equal heights: moving L++ is conventional — no pair is skipped or double-counted regardless of choice.

✓

Total moves: L and R together advance exactly n−1 times, visiting every necessary pair.

Step 9

Approaches

Time O(n)Space O(1)

One sweep. Five variables. Greedy proof guarantees correctness. The approach above.

Time O(n²)Space O(1)

Two nested loops, check every pair. Correct but TLE for n>10⁴. Shown in the brute force section.

Step 10

Complexity

Time

O(n)

L and R together advance n−1 steps total. Single pass, no inner loop.

Space

O(1)

Six variables: L, R, best, cap, width, area. No extra arrays.

Take home

What to remember for similar problems

The monotonic trade-off principle: two pointers work whenever one pointer's move is provably dominated. Here, moving the taller pointer shrinks width with zero upside on the cap. Identify this structure first — "one side's move can only hurt" — and the algorithm falls out immediately.

Contrast with Trapping Rain Water (LC #42): both use the bottleneck principle, but there every bar contributes water, not just two endpoints. That forces tracking running maxes from both sides simultaneously rather than a single running best.

Related: LC 42 (Trapping Rain Water — same bottleneck idea, every bar contributes), LC 15 (3Sum — inward two pointers but sorted array and sum condition, not area maximization).
