Coin Change

LC #322 Medium Dynamic Programming

Before you code

Clarifying questions to ask first

Ask these before writing anything. Each answer constrains what the solution needs to handle.

Can the same coin be used many times?
Yes — coin supply is unbounded. Picking a 5 once doesn't stop us from picking another 5.
→ unlocks: dp[i] may revisit the same coin from dp[i−c]; this is unbounded knapsack, not 0/1 — we don't track "used".
What if the amount can't be made from the given coins?
Return −1.
→ unlocks: need a sentinel for "unreachable" distinct from any real coin count — use amount+1 (no honest answer can exceed amount 1-coins).
Are coin values always positive integers?
Yes — coins are in [1, 2³¹−1] and all distinct.
→ unlocks: no zero coin (would loop forever); no negatives (would break monotone subproblem ordering — dp[i] depends on dp[i−c] with c ≥ 1).
What's the range of amount?
0 ≤ amount ≤ 10⁴. Note that 0 is legal — answer is 0.
→ unlocks: O(amount × |coins|) table is ~10⁶ ops — comfortably fast. Must handle amount=0 (loop body never runs, return dp[0]=0).

Assumptions we carry forward

Coins are positive integers, repeatable. We need the fewest coins (not the number of ways). Return −1 if impossible. amount=0 means zero coins.

The Insight

The last coin splits the problem in two: one coin, plus a smaller version of the same problem

Whatever the optimal coin set for amount N looks like, it must end with some coin c. Strip that coin off and what remains is the optimal coin set for amount N−c — the same problem, smaller. So the answer at N is decided by the answers at amounts strictly below it.

Step 1

Brute force — feel the cost

If you just write the recurrence directly — f(n) = 1 + min(f(n−c)) — and recurse without remembering anything, the same subproblem is computed over and over. The call tree branches by |coins| at each level and is up to amount/min_coin deep, so the work is exponential. Watch the calls counter explode on small inputs.

arg: — depth: 0 calls: 0

Cost: O(|coins|amount/min_coin) time, O(amount) stack

The same subproblem (e.g. f(2)) is recomputed under many different paths. For amount=5, coins=[1,2,5] that's already 20+ calls; for amount=30 it's millions. The fix is to remember each subproblem's answer once — dynamic programming.

int solve(vector<int>& coins, int n) {
    if (n == 0) {
        return 0;
    }
    if (n < 0) {
        return INT_MAX;            // unreachable
    }
    int best = INT_MAX;
    for (int c : coins) {
        int sub = solve(coins, n - c);
        if (sub != INT_MAX) {
            best = min(best, sub + 1);
        }
    }
    return best;
}

int coinChange(vector<int>& coins, int amount) {
    int r = solve(coins, amount);
    return r == INT_MAX ? -1 : r;
}

Step 2

Translations — every optimisation, named

Three concrete moves carry us from the exponential recursion to the linear table: re-frame the recurrence as a subproblem table, fill it bottom-up so every dependency is already computed, and choose a sentinel that distinguishes "no path yet" from "zero coins".

1
"Fewest coins for N" → "1 + fewest coins for N−c, taken over coins c"
The last-coin decomposition. Whatever optimal solution exists for N, peel off its last coin c; what remains is the optimal solution for N−c. So the answer at N is one more than the smallest answer over all reachable predecessors.
→ recursion shape becomes a clean recurrence: dp[i] = 1 + min over c of dp[i−c]
2
"For every amount below N" → 1-D table dp[0..N], filled left-to-right
Because c ≥ 1, every dependency dp[i−c] sits at a strictly smaller index than i. Filling in increasing order of i guarantees those cells are already finalised when we read them — no recursion, no memoisation overhead.
→ exponential recursion → O(amount × |coins|) iteration, O(amount) memory
3
"Impossible / not yet reachable" → sentinel value amount+1
We need to write a number into every cell, even unreachable ones, so that min(…) still works. Use amount+1: it's larger than any real answer (which is at most amount, using all 1-coins) and fits in an int without overflow risk. At the end, dp[amount] > amount means unreachable → return −1.
→ no special-case branching inside the loop; one clean min() expression

Step 3

The algorithm in plain English

1Allocate dp of length amount+1; fill every cell with the sentinel amount+1, then set dp[0]=0.
2For each target i from 1 to amount:
3For each coin c: if c ≤ i, compute dp[i−c]+1 and keep the running minimum as dp[i].
4After the table is filled: if dp[amount] > amount the target is unreachable — return −1.
5Otherwise return dp[amount].

Step 4

Code

int coinChange(vector<int>& coins, int amount) {
    vector<int> dp(amount + 1, amount + 1);
    dp[0] = 0;
    for (int i = 1; i <= amount; i++) {
        for (int c : coins) {
            if (c <= i) {
                dp[i] = min(dp[i], dp[i - c] + 1);
            }
        }
    }
    if (dp[amount] > amount) {
        return -1;
    }
    return dp[amount];
}

Step 7

Corner cases

1
amount = 0 — empty target
dp has one cell, dp[0]=0; the outer loop's range is 1..0 which never executes. Returns 0 cleanly — no special case needed.
2
coins=[2], amount=3 — unreachable
dp[1] and dp[3] never get updated; they stay at sentinel amount+1=4. The final check dp[amount] > amount catches this and returns −1.
3
coins=[3], amount=9 — only multiples reachable
dp[3]=1, dp[6]=2, dp[9]=3; the non-multiples (1, 2, 4, 5, 7, 8) stay sentinel. The min() never picks them because they're larger than amount. Answer 3.
4
Coin larger than amount
The guard c <= i skips those coins. A 100-valued coin contributes nothing while we're filling dp[1..99]; no crash, no off-by-one.
5
Greedy temptation: coins=[1,3,4], amount=6
Greedy "take the biggest coin that fits" picks 4+1+1=3 coins. The DP correctly finds 3+3=2 coins. Mentioning this in an interview shows you know greedy fails here — and why the DP is necessary.

Step 8

Production readiness

✓
amount = 0 — falls out: outer loop never runs, dp[0]=0 is returned directly. No special-case.
✓
Unreachable amount — sentinel amount+1 survives in dp[amount]; the final dp[amount] > amount check returns −1.
✓
Coin > remaining — the c <= i guard skips it; no out-of-bounds read of dp[i−c].
✓
Integer overflow — sentinel is amount+1 ≤ 10⁴+1; adding 1 in dp[i−c]+1 stays well inside int. Avoid INT_MAX as sentinel (then +1 overflows).
✓
Off-by-one — dp size is amount+1 (indices 0..amount inclusive); outer loop is i <= amount, not <.
✓
Greedy pitfall — do not "take the largest coin that fits"; counterexample [1,3,4], amount=6 proves it can be wrong.
✓
Coin order independence — the inner min() commutes; coins do not need to be sorted. Sorting can let you break early once c > i, a minor constant-factor win.

Step 9

Approaches — trade-offs

O(amount · |coins|) O(amount)

The reference solution. One pass over the dp table, no recursion, no hash map. Sentinel amount+1 keeps the inner expression branch-free. This is the default answer in an interview because it's iterative, simple to reason about, and fits naturally in the lower bound (you genuinely do need to know dp[i] for every i ≤ amount in the worst case).

int coinChange(vector<int>& coins, int amount) {
    vector<int> dp(amount + 1, amount + 1);
    dp[0] = 0;
    for (int i = 1; i <= amount; i++) {
        for (int c : coins) {
            if (c <= i) {
                dp[i] = min(dp[i], dp[i - c] + 1);
            }
        }
    }
    return dp[amount] > amount ? -1 : dp[amount];
}
O(amount · |coins|) O(amount) heap + O(amount) stack

Mirrors the recurrence directly: a recursive function solve(n) returning the answer for amount n, with a memo array so each subproblem is solved once. Same asymptotic cost as bottom-up but pays recursion overhead and risks stack depth at amount=10⁴ (most languages handle this, but it's worth flagging). Worth mentioning if the interviewer asks "how would you write this recursively?"

vector<int> memo;

int solve(vector<int>& coins, int n) {
    if (n == 0) {
        return 0;
    }
    if (memo[n] != -2) {
        return memo[n];
    }
    int best = INT_MAX;
    for (int c : coins) {
        if (c <= n) {
            int sub = solve(coins, n - c);
            if (sub != -1 && sub != INT_MAX) {
                best = min(best, sub + 1);
            }
        }
    }
    memo[n] = (best == INT_MAX) ? -1 : best;
    return memo[n];
}

int coinChange(vector<int>& coins, int amount) {
    memo.assign(amount + 1, -2);
    return solve(coins, amount);
}
O(amount · |coins|) O(amount)

Treat amounts as graph nodes and each coin as an edge of weight 1. BFS from 0 finds the shortest path to amount, which is the fewest coins. Same asymptotic complexity, but BFS can terminate early the moment it dequeues amount — sometimes much faster on inputs with a shallow answer. Worth mentioning when the interviewer presses on the worst case vs. typical case.

int coinChange(vector<int>& coins, int amount) {
    if (amount == 0) {
        return 0;
    }
    vector<bool> seen(amount + 1, false);
    queue<int> q;
    q.push(0);
    seen[0] = true;
    int level = 0;
    while (!q.empty()) {
        level++;
        int sz = q.size();
        while (sz--) {
            int cur = q.front(); q.pop();
            for (int c : coins) {
                int nxt = cur + c;
                if (nxt == amount) {
                    return level;
                }
                if (nxt < amount && !seen[nxt]) {
                    seen[nxt] = true;
                    q.push(nxt);
                }
            }
        }
    }
    return -1;
}

Step 10

Complexity

Time
O(amount · |coins|)
The outer loop runs amount times; the inner loop tries every coin and does O(1) work per pair.
Space
O(amount)
The dp table holds amount+1 integers. No recursion, so stack depth is O(1).
