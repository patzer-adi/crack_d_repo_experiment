Count Permutations With Inversion Requirements

LC #3376 Hard Dynamic Programming

Before you code

Clarifying questions to ask first

What is an inversion?

A pair (i,j) where i < j but perm[i] > perm[j] — a larger value appears before a smaller one.

→ counting inversions is a classic DP sub-problem

What does a requirement [end, cnt] mean?

The prefix perm[0..end] must contain exactly cnt inversions. Multiple requirements may exist.

→ requirements act as hard constraints at specific prefix lengths

Can requirements conflict?

Yes — e.g. requiring 5 inversions at index 1 is impossible (max is 1). Return 0.

→ always check feasibility; impossible states get zeroed out

What do we return?

Count of valid permutations modulo 10⁹+7.

→ apply mod at every addition step

Assumptions we carry forward

Permutation is of [0, 1, 2, …, n−1]. Requirements are guaranteed to reference valid end indices (0 ≤ end < n). Multiple requirements may target the same end index — but the problem guarantees each end appears at most once. We count modulo 10⁹+7.

The Insight

What is an inversion — and why insertion builds them

An inversion is any pair of positions where a larger value sits to the left of a smaller one. In the permutation [2, 0, 1]: the pair (2,0) and (2,1) are both inversions — two inversions total.

The kernel

Define dp[i][j] = number of permutations of the first i+1 elements with exactly j inversions that satisfy all requirements up to index i. When inserting element i, it can add 0 to i new inversions — so dp[i][j] = sum of dp[i−1][j−k] for k in 0..min(i,j). At each required index, zero out all states except the required inversion count. Use a prefix-sum sliding window to evaluate each row in O(max_inv) instead of O(i·max_inv).

Step 1

Brute force: generate all permutations and check each

Generate every permutation of [0..n−1]. For each, check whether every prefix satisfies its requirement. Count those that pass all checks.

checked: 0  ·  valid: 0

Cost: O(n! × n) time

n! permutations, each taking O(n) to check inversions. For n=13: 13! ≈ 6×10⁹ — completely infeasible.

Step 2

Three translations to O(n × max_inv)

The brute force generates and checks. The DP approach counts directly — never enumerating individual permutations.

1

Translation 1 — Count by building, not enumerating

Instead of generating permutations and checking, build them incrementally. dp[i][j] = number of ways to arrange the first i+1 elements with exactly j inversions satisfying all requirements ≤ i. The DP recurrence comes from the insertion observation: inserting element i in position k from the right adds exactly k new inversions.

→ O(n!) enumerate → O(n × max_inv) count

2

Translation 2 — Requirements zero out invalid states

After computing dp[i], if index i has a requirement cnt: set every dp[i][j] to 0 where j ≠ cnt. Only the required inversion count survives. This propagates the constraint forward — future rows build only from valid states.

if req[i] exists: keep only dp[i][req[i]], zero the rest
// impossible requirement → dp[i][req[i]]==0 → all future rows = 0

→ constraints enforced inline, no post-filtering needed

3

Translation 3 — Sliding window prefix sum for O(1) per cell

The recurrence dp[i][j] = Σ dp[i−1][j−k] for k in 0..min(i,j) is a sliding window sum of at most i+1 consecutive cells of dp[i−1]. Build a prefix sum of dp[i−1] once per row. Each dp[i][j] = prefix[j+1] − prefix[max(0, j−i)]. One O(max_inv) pass replaces O(i × max_inv) per row.

prefix[j+1] = prefix[j] + dp[j]
dp_new[j] = prefix[j+1] - prefix[max(0, j-i)]

→ O(n × max_inv²) naive DP → O(n × max_inv) with prefix sums

Step 3

The algorithm in plain English

Say this before writing any code.

1.Build req[]: an array of length n, initialized to -1. For each [end, cnt] in requirements, set req[end] = cnt.
2.Initialize dp[0] = 1, all others 0. If req[0] exists and is not 0, return 0 immediately (single element always has 0 inversions).
3.For i from 1 to n−1: build a prefix sum of the current dp array. Compute new_dp[j] = prefix[j+1] − prefix[max(0, j−i)] for each j. This is the sliding window sum.
4.If req[i] ≥ 0: keep only new_dp[req[i]], zero all other slots. Replace dp with new_dp.
5.Return sum(dp) mod 10⁹+7. If any requirement was impossible, dp will be all zeros and the sum is 0.

Why the window size is exactly i+1

When inserting element i into a sequence of i existing elements, you can place it in positions 0 through i — creating 0 to i new inversions. So dp[i][j] depends on dp[i−1][j], dp[i−1][j−1], …, dp[i−1][j−i]. That is a window of at most i+1 consecutive cells. The window never grows larger than i+1 regardless of j.

Step 4

Canonical C++ solution

Try writing from the five steps above before revealing.

int countPermutations(int n, vector<vector<int>>& requirements) {
    const int MOD = 1e9 + 7;
    int maxInv = n * (n - 1) / 2;

    // Build req[] — inversion requirement at each index (-1 = no req)
    vector<int> req(n, -1);
    for (auto& r : requirements) { req[r[0]] = r[1]; }

    // Base case: one element, always 0 inversions
    vector<long long> dp(maxInv + 1, 0);
    dp[0] = 1;
    if (req[0] != -1 && req[0] != 0) { return 0; }

    for (int i = 1; i < n; i++) {
        // Build prefix sum of current dp
        vector<long long> prefix(maxInv + 2, 0);
        for (int j = 0; j <= maxInv; j++) {
            prefix[j + 1] = (prefix[j] + dp[j]) % MOD;
        }

        // Sliding window: new_dp[j] = sum of dp[j-i .. j]
        vector<long long> new_dp(maxInv + 1, 0);
        for (int j = 0; j <= maxInv; j++) {
            int lo = max(0, j - i);
            new_dp[j] = (prefix[j + 1] - prefix[lo] + MOD) % MOD;
        }

        // Enforce requirement if present at index i
        if (req[i] != -1) {
            long long keep = new_dp[req[i]];
            fill(new_dp.begin(), new_dp.end(), 0);
            new_dp[req[i]] = keep;
        }

        dp = new_dp;
    }

    long long ans = 0;
    for (auto v : dp) { ans = (ans + v) % MOD; }
    return (int)ans;
}

Step 7

Corner cases

1

Impossible requirement — req[end] > end*(end+1)/2

A prefix of length end+1 can have at most end*(end+1)/2 inversions. If the requirement exceeds this, new_dp[req[i]] is already 0 after the DP step. The zero propagates forward — final answer is 0.

2

Requirement at index 0

A single-element prefix has exactly 0 inversions always. If req[0] exists and is not 0, return 0 immediately before any loop. If req[0] == 0, dp stays [1, 0, 0, …] and the loop proceeds normally.

3

No requirements at all

req[] is all -1. The DP runs freely — no zeroing happens. The final sum(dp) equals n! (all permutations of n elements), which is the expected answer when there are no constraints.

4

Requirement at the last index only

The DP builds freely until i = n−1. At the last step, only new_dp[req[n−1]] survives. The answer is exactly that one value — the number of full permutations with the required inversion count.

5

Prefix subtraction goes negative (mod arithmetic)

prefix[j+1] - prefix[lo] can be negative before mod when values are large. Always add MOD before taking mod: (prefix[j+1] - prefix[lo] + MOD) % MOD.

Step 8

Production readiness

✓

req[0] != 0: early return 0 before allocating any arrays.

✓

Negative mod: (prefix[j+1] - prefix[lo] + MOD) % MOD — the +MOD prevents negative results.

✓

maxInv size: dp array has maxInv+1 = n(n−1)/2+1 slots. For n=13: 79 slots — small and safe.

✓

Impossible requirement propagates to 0: if new_dp[req[i]]==0 after DP, the zero carries through all subsequent rows. Final sum is 0. No explicit zero-check needed.

✓

Integer type: use long long for dp and prefix arrays — intermediate products can exceed int range before mod.

Step 9

Approaches

Time O(n × maxInv)Space O(maxInv)

One dp array of size maxInv+1, updated n−1 times. Each update is O(maxInv) with prefix sum. maxInv = n(n−1)/2. Total: O(n³) which for typical constraints (n≤13) is instant.

Time O(n² × maxInv)Space O(maxInv)

Same DP but compute each new_dp[j] by iterating k from 0 to min(i,j) explicitly. O(i) work per cell instead of O(1). Still correct, just slower. Fine for n≤13 but the prefix sum version is cleaner.

Time O(n! × n)Space O(n)

Generate all n! permutations, check each prefix against all requirements. Infeasible for n > 10.

Step 10

Complexity

Time

O(n × M)

M = maxInv = n(n−1)/2. n−1 outer iterations, each O(M) with prefix sum. Total O(n × n²) = O(n³) — fast for n≤13.

Space

O(M)

Two dp arrays of size M+1 (current and new), plus prefix array. No 2D table stored — one row at a time.

Take home

What to remember for similar problems

The insertion DP for inversions is a classic pattern: inserting element i into a sequence of i elements can create 0 to i new inversions, so dp[i][j] = Σ dp[i−1][j−k] for k in 0..min(i,j). This sliding-window sum structure appears whenever the recurrence is "sum over a contiguous window of the previous row."

The constraint zeroing technique — keeping only one cell of a DP row and zeroing the rest — is a clean way to enforce exact-value requirements mid-DP. It propagates forward automatically: if the required value is unreachable, the zero spreads through all future rows.

Related: LC 629 (K Inverse Pairs Array — same insertion DP for counting permutations with exactly k inversions, no intermediate constraints), LC 315 (Count of Smaller Numbers After Self — counting inversions directly via merge sort or BIT), LC 493 (Reverse Pairs — harder inversion variant).
