Two Sum II — Input Array Is Sorted

LC #167 Medium Two Pointers

Before you code

Clarifying questions to ask first

Ask these before writing anything. Each answer constrains what the solution needs to handle.

Is the input guaranteed sorted (ascending)?

Yes — that is the whole point. The array is sorted non-decreasing.

→ unlocks the two-pointer squeeze; no hash map needed

Is there exactly one solution?

Yes. Exactly one pair sums to the target, and an element may not be used twice.

→ we can return immediately on the first match

What index base does the answer use?

1-indexed. Return positions [i+1, j+1], not the raw array indices.

→ add 1 to both pointers in the returned pair

Can values be negative or repeated?

Yes to both — values may be negative and duplicates are allowed.

→ the squeeze relies only on order, so signs and repeats are fine

Assumptions we carry forward

Sorted ascending, exactly one answer, 1-indexed output, values may be negative or duplicated. O(1) extra space is expected (the array is already sorted, so a hash map is wasteful).

The Insight

Sorted order turns the sum into a dial you can steer

Because the array is sorted, the smallest possible sum is the two leftmost elements and the largest is the two rightmost. Put one pointer at each end and read their sum. If it is too small, the only way to grow it is to give up the smallest element — move the left pointer right. If it is too large, the only way to shrink it is to give up the largest element — move the right pointer left. Every move strictly tightens the window toward the target and permanently discards an element that could never be part of the answer, so a single inward sweep either lands on the target or proves no pair exists. No element is ever revisited, which is why O(n²) checking collapses to O(n).

numbers = [2, 7, 11, 15]  ·  target = 9  ·  L = left  ·  R = right
left pointer (L) right pointer (R) matched pair

The kernel

Set L = 0, R = n − 1. Loop while L < R: let sum = numbers[L] + numbers[R]. If sum == target, return [L+1, R+1]. If sum < target, do L++ (need a bigger value). If sum > target, do R-- (need a smaller value). Sortedness guarantees each discarded element is genuinely impossible, so the squeeze is correct and runs in O(n).

Step 1

Brute force — feel the cost

Ignore the sortedness and just try every pair: for each i, scan every j > i and test whether the two add to the target. It works, but it inspects up to n(n−1)/2 pairs. Watch the "Checks" counter climb — on the longer example it does far more work than the single inward sweep we build next, which never re-examines an element.

vector<int> twoSum(vector<int>& numbers, int target) {
    int n = numbers.size();
    for (int i = 0; i < n; i++) {
        for (int j = i + 1; j < n; j++) {
            if (numbers[i] + numbers[j] == target) {
                return {i + 1, j + 1};
            }
        }
    }
    return {};
}

Step 2

Translations — every optimisation, named

Two ideas take the naive double loop down to a single linear pass — each one exploits the fact that the array is already sorted.

1

Replace the inner search with a hash map

For each numbers[i], look up target − numbers[i] in a hash set of seen values. This is the generic "Two Sum" trick and works on unsorted input too.

O(n²) time → O(n) time, but O(n) extra space

2

Exploit the sort: converging two pointers

Since the array is sorted, the sum of the two ends is monotonic in each pointer. Start wide and move the pointer that steers the sum toward the target. No hash map, no second pass.

O(n) extra space → O(1)

3

Return on first match

The problem guarantees exactly one solution, so the instant sum == target we can return [L+1, R+1] — no need to keep scanning or collect multiple results.

early exit; never over-runs the answer

Step 3

The algorithm in plain English

1.Place L at the first index and R at the last.
2.While L < R, add numbers[L] + numbers[R].
3.If the sum equals the target, return [L+1, R+1].
4.If the sum is too small, advance L to pick up a larger value.
5.If the sum is too large, retreat R to pick up a smaller value.
6.Stop when the pointers meet — by the guarantee, a match is always found first.

Step 4

Code

vector<int> twoSum(vector<int>& numbers, int target) {
    int L = 0, R = (int)numbers.size() - 1;
    while (L < R) {
        int sum = numbers[L] + numbers[R];
        if (sum == target) {
            return {L + 1, R + 1};
        } else if (sum < target) {
            L++;
        } else {
            R--;
        }
    }
    return {};
}

Step 7

Corner cases

1

Match on the first check

[1,2], t=3 — the two ends already sum to the target, so the loop returns [1,2] on its very first iteration.

2

Negative numbers

[-3,3,4], t=0 — sortedness still holds for negatives, so the squeeze works unchanged: -3 + 4 = 1 > 0 → R--, then -3 + 3 = 0 → [1,2].

3

Duplicate values

[1,2,3,4,4,9,56,90], t=8 — the two equal 4s form the pair. The squeeze finds the correct two positions because it compares the ends, not the values' uniqueness.

4

1-indexed output

Forgetting the +1 is the classic bug. The array is 0-indexed internally but the answer must be 1-indexed — return [L+1, R+1].

5

Two-element array

[a,b] — L=0, R=1, one check. If they sum to target return [1,2]; otherwise the loop ends immediately.

Step 8

Production readiness

✓Termination: every iteration moves L right or R left, so the gap strictly shrinks and the loop always ends.
✓Correctness: discarding the smallest (or largest) end is provably safe — it cannot pair with anything remaining to hit the target.
✓Overflow: for large values, compute sum as long long to avoid int overflow before the comparison.
✓1-indexing: the returned pair adds 1 to both pointers — verified against the problem's examples.
✓Space: O(1) — no hash map, since the sort already encodes the ordering a map would rebuild.
✓No-solution path: the trailing return {} is defensive even though the prompt guarantees a solution.

Step 9

Approaches — trade-offs

Time O(n)Space O(1)

The optimal answer for a sorted input. One inward sweep, constant space, returns on first match. This is what to write here.

int L = 0, R = (int)numbers.size() - 1;
while (L < R) {
    int s = numbers[L] + numbers[R];
    if (s == target) return {L + 1, R + 1};
    else if (s < target) L++;
    else R--;
}
Time O(n)Space O(n)

The generic Two Sum trick: store each value in a hash map and look up the complement. Works on unsorted input, but wastes O(n) space rebuilding ordering the sort already gave us.

unordered_map<int,int> seen;
for (int i = 0; i < (int)numbers.size(); i++) {
    auto it = seen.find(target - numbers[i]);
    if (it != seen.end()) return {it->second + 1, i + 1};
    seen[numbers[i]] = i;
}
Time O(n log n)Space O(1)

For each i, binary-search the array for target − numbers[i]. Uses the sort but only halfway — it still pays a log factor per element instead of the linear squeeze.

for (int i = 0; i < (int)numbers.size(); i++) {
    int need = target - numbers[i];
    auto it = lower_bound(numbers.begin() + i + 1, numbers.end(), need);
    if (it != numbers.end() && *it == need)
        return {i + 1, (int)(it - numbers.begin()) + 1};
}
