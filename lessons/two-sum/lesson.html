Before you code

Clarifying questions to ask first

Ask these before writing anything. Each answer constrains what the solution needs to handle.

Is exactly one solution guaranteed?

Yes — the problem promises exactly one valid pair.

→ return on first hit; no need to enumerate

Can the same element be used twice?

No — indices i and j must be distinct.

→ probe map for complement before inserting nums[i]

Can the input contain duplicate values?

Yes — e.g. [3,3] with target 6 is valid.

→ a later duplicate finds the earlier one; overwrite is safe

Do indices need to be sorted in the output?

No — any order is accepted.

→ return [seen[c], i] directly; no extra sort

Assumptions we carry forward

Input is an unsorted array of integers (negatives allowed). Target is an integer (negative allowed). Exactly one pair exists. Output is the two original indices — sortedness of the input is not a resource we have, and we cannot afford to lose original positions by sorting.

The Insight

Trade a backward scan for a hash lookup.

At index i, the question is not "do any two elements sum to target?" — it is "has the value target − nums[i] appeared before now?" The two phrasings have the same answer, but the second one is asked once per element, not once per pair. The savings come entirely from how fast we can answer "have I seen value c, and at what index?" — O(n) with a linear backscan, O(1) with a hash map.

The kernel

Walk i from 0 to n−1. Keep a hash map seen from value to index, holding everything visited so far. At each i, probe first for target − nums[i]; on hit, return [seen[complement], i]. On miss, insert nums[i] → i. Probe-before-insert keeps seen aligned with indices < i, so an element can never match itself.

Step 1

Brute force: every pair

For each index i, try every later index j > i; check if nums[i] + nums[j] == target. Two nested loops over n elements. The work grows with the number of pairs — about n²/2 in the worst case.

i=—  j=—  ·  sum: —  ·  checks: 0

Cost: O(n²) time, O(1) space

Two nested loops over n elements. Worst case (answer at the end, or no early-return) is C(n,2) ≈ n²/2 checks. For LC's 10⁴ limit that is up to 5×10⁷ comparisons — borderline TLE on a stricter judge.

vector<int> twoSum_BF(vector<int>& nums, int target) {
    int n = nums.size();
    for (int i = 0; i < n - 1; i++) {
        for (int j = i + 1; j < n; j++) {
            if (nums[i] + nums[j] == target) {
                return {i, j};
            }
        }
    }
    return {};  // problem guarantees a solution, never reached
}

Step 2

Two translations from O(n²) to O(n)

The brute force asks "do these two add to target?" once per pair. Two translations turn that into one lookup per element.

1

Translation 1 — Pair search → complement search

For each i, instead of testing every j, ask one question: "has the value target − nums[i] appeared at any earlier index?" Same answer set; very different work. The outer loop is still O(n), but the inner question is now a single lookup against the prefix nums[0..i−1] — not a full scan of it. e.g. at nums[i]=7, target=9, we look for value 2 in everything seen so far.

→ work per element: "is there a partner?" instead of "test every partner"

2

Translation 2 — Linear lookup → hash lookup, in one pass

"Has value c appeared, and at what index?" is exactly what a hash map answers. Maintain seen = (value → index) of everything visited; at index i, probe first, then insert. Probe-before-insert keeps seen equal to indices < i, so an element can never match itself — no i ≠ j guard, no second pass. Each step is O(1) average; total is O(n).

c = target − nums[i]
seen[c] exists → return [seen[c], i]
else → seen[nums[i]] = i  // insert AFTER the probe

→ per-step lookup O(n) → O(1) average · total O(n²) → O(n)

Why "probe before insert" — and not the other way around

If you inserted nums[i] first and then probed, an element could find itself: e.g. nums=[3,…], target=6 would probe for value 3 and find the 3 you just stored at index i — falsely returning [i, i]. Probe-before-insert sidesteps the bug entirely: at the moment of probing, the map contains only indices < i. (Duplicate values still work: in [3,3], the second 3 probes and finds the first 3, which was stored on the previous iteration.)

Step 3

The algorithm in plain English

1.Create an empty hash map seen from value to index.
2.Walk i from 0 to n−1.
3.Compute complement = target − nums[i].
4.If seen contains complement, return [seen[complement], i].
5.Otherwise store seen[nums[i]] = i and continue.
6.The problem guarantees a solution, so the loop always returns before exhausting nums.

Step 4

Code

vector<int> twoSum(vector<int>& nums, int target) {
    unordered_map<int, int> seen;          // value → index
    int n = nums.size();
    for (int i = 0; i < n; i++) {
        int complement = target - nums[i];
        if (seen.count(complement)) {
            return {seen[complement], i};
        }
        seen[nums[i]] = i;                  // insert AFTER probe
    }
    return {};                              // unreachable: problem guarantees a solution
}

Step 7

Corner cases

1

Duplicate value forms the answer — [3, 3], target = 6

i=0: complement = 3, seen empty, miss → store seen[3] = 0. i=1: complement = 3, seen[3] = 0, hit → return [0, 1]. The second copy finds the first because we probe before we'd overwrite. If we'd inserted before probing, the second copy would have overwritten index 0 and self-matched.

2

Same element can't be reused — guaranteed by ordering, not by a guard

No explicit i ≠ j check appears in the code. It is implicit in the order of operations: at index i, seen contains only indices < i, so the answer it returns is always paired with an earlier index. [2, 4, 4] with target = 8 returns [1, 2], not [1, 1], because the first 4 is in seen when the second 4 probes.

3

Negative numbers and negative target — [-1, -2, -3, -4, -5], target = -8

Hashing is value-agnostic — integer hashes don't care about sign. i=2: complement = -8 − (-3) = -5, miss. … i=4: complement = -8 − (-5) = -3, seen[-3] = 2, hit → return [2, 4]. No casting, no offset, no special case.

4

Answer at the very end — [3, 2, 4], target = 6

i=0..1 are misses that just populate seen. i=2: complement = 2, hit → [1, 2]. The loop must visit every earlier index before the final partner triggers a hit; do not write code that "looks ahead" or terminates early. Early termination would lose the answer.

5

Why a two-pass "fill then scan" version is wrong

A two-pass version inserts every nums[i] → i first, then re-scans probing for complements. On [3, 3] with target 6 that probes for value 3 at i=0 and finds seen[3] = 1 — returning [0, 1] by luck; but on [3, 4] with target 6 it probes for 3 at i=0 and finds seen[3] = 0, returning the bogus [0, 0]. The single-pass probe-before-insert order is what avoids this entire class of bug.

Step 8

Production readiness

✓

Probe before insert: the order of operations is the no-self-pair guard. Never swap them.

✓

Use count() or find(), not operator[], for the probe: seen[c] would insert a default-zero entry on a miss, silently corrupting the map.

✓

Reserve capacity for large inputs: seen.reserve(nums.size()) on unordered_map trades a touch of memory for fewer rehashes — measurable on 10⁴+ inputs.

✓

Integer overflow: target − nums[i] with INT_MIN ≤ nums[i] ≤ INT_MAX and a large positive target can overflow int. LC's stated bounds (|nums[i]| ≤ 10⁹, |target| ≤ 10⁹) keep the subtraction inside int — but on stricter input bounds, widen to long long.

✓

Unreachable return: return {}; after the loop documents that the problem guarantees a solution. Do not raise — the judge expects a vector.

✓

Don't pre-fill the map: a two-pass version (fill then scan) can self-match. The one-pass probe-before-insert is the correctness-critical structure, not an optimisation.

Step 9

Approaches

Time O(n)Space O(n)

The solution taught in §4–§5. Walk once, probe-then-insert. Optimal time complexity — you must read every element at least once when the answer is at the end. The space cost buys the O(1) average lookup that makes the linear time possible.

Time O(n log n)Space O(n)

Sorting destroys index information — and "return the original indices" is exactly what the problem asks for. To recover, sort pairs (value, original_index) instead of bare values, then squeeze L and R inward. (Another way to put it: this is what you'd do if the problem returned values; the hash map is what you do because it returns indices.) Strictly worse than the hash map on this exact problem, but it generalises cleanly to Two Sum II (sorted input, O(1) extra space) and to 3Sum / 4Sum.

vector<int> twoSum_sort(vector<int>& nums, int target) {
    int n = nums.size();
    vector<pair<int, int>> vi(n);
    for (int i = 0; i < n; i++) {
        vi[i] = {nums[i], i};                  // keep original index
    }
    sort(vi.begin(), vi.end());                // O(n log n)
    int L = 0, R = n - 1;
    while (L < R) {
        int s = vi[L].first + vi[R].first;
        if (s == target) {
            return {vi[L].second, vi[R].second};
        } else if (s < target) {
            L++;
        } else {
            R--;
        }
    }
    return {};
}
Time O(n²)Space O(1)

Two nested loops, return on first hit. Correct and tiny. Fast enough at LC's 10⁴ limit, but a clear signal in an interview that you didn't reach for the obvious O(n) improvement. The starting point that motivates the two translations in §3.

Step 10

Complexity

Time

O(n)

One pass; each step does an O(1) average hash probe and an O(1) average insert. Worst case is O(n) per step under adversarial hashing, but unordered_map's amortised guarantees give O(n) total in practice.

Space

O(n)

The map stores at most n entries before the answer is found. The answer vector is two ints. No recursion, no stack depth concerns.

Take home

What to remember for similar problems

The pattern: scan once, ask "have I seen the complement?" against a value→index map, probe before insert. The order of operations is what guarantees correctness without an explicit i ≠ j guard.

A hash map is the right answer when the inner question is "has value X appeared, and where?" — i.e. an exact-key lookup. The moment the question becomes "is there an X in some range?", the hash map stops being enough and you need sorting + two-pointer (or a BIT / segment tree).

Related problems:

LC 167 — Two Sum II (Sorted) — same question with sorted input and indices not required. Hash map still works, but the canonical answer is O(1)-space two-pointer. Teaches that sortedness is a real algorithmic resource.

LC 15 — 3Sum — triples summing to 0. Hash map struggles with duplicate-triple dedup; the optimal is sort + two-pointer per fixed outer index. Different translation for a different constraint.

LC 653 — Two Sum IV (BST) — same complement question over a tree. The hash-map approach ports verbatim (any traversal). Shows the technique is data-structure-portable.

LC 1099 — Two Sum Less Than K — maximum sum strictly less than K. Hash map breaks because we'd need a range query, not an exact-key probe. Optimal is sort + two-pointer.
