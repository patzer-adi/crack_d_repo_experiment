Repeated String Match

LC #686 Medium String Matching

Before you code

Clarifying questions to ask first

Ask these before writing anything. Each answer constrains what the solution needs to handle.

A boolean, or a count?
Return the minimum number of copies of a whose concatenation contains b, or -1 if no number works.
→ the answer is a plain integer; the oracle compares with ===, no ordering subtleties
Can the answer be 1?
Yes — when b already sits inside a single a. It is never 0 (zero copies is the empty string).
→ the floor is ⌈n/m⌉ ≥ 1, where m = |a|, n = |b|
When is it impossible?
When b contains a character not in a, or a run the periodic tiling of a never produces.
→ after the bounded check fails, return -1 — do not loop forever
How large can the strings be?
Up to ~10⁴ each. Building b plus two extra copies of a and one search is O(m + n).
→ the naive unbounded loop is the trap, not the search itself

The Insight

b can only sit inside the tiling of a at some offset — and that pins the copy count to just two candidates

You probably wrote a loop that keeps gluing another copy of a onto a growing string and checking whether b is inside — and on an impossible b it never stops. Step back: b can only appear in the periodic tiling a a a … if it lines up at some starting offset, and that single fact pins the number of copies you ever need to exactly two candidates.

Two bounds squeeze the answer:
⌈n/m⌉
Length floor — you need at least this many copies
To even fit an n-char b, the tiling must be at least length n. That is ⌈n/m⌉ copies — fewer cannot possibly hold b.
+1
Offset ceiling — one extra copy for the worst alignment
b need not start at a copy boundary; it can begin as far as offset m−1 into the first copy, pushing its tail into one more copy. So ⌈n/m⌉ + 1 copies cover every possible starting offset.
−1
Beyond that, nothing new — so stop
The tiling is periodic with period m. Any length-n window not seen within ⌈n/m⌉+1 copies has already repeated, so longer tilings add nothing. If b is absent by then, it is absent forever → -1.

The kernel

Let m = |a|, n = |b|. Build a repeated k = ⌈n/m⌉ times and test whether b is a substring; if not, append one more a and test again. The answer is k, or k+1, or — if neither tiling contains b — -1. Two substring searches decide everything, because periodicity means no longer repetition can produce a window the first k+1 copies didn't.

Step 1

Brute force — feel the cost

The most mechanical idea: start with one copy of a, search for b, and if it is missing append another copy and search again — repeat. It finds the answer for any b that is reachable, but watch the trap: it has no stopping rule, so for an impossible b it appends copies forever.

tiling  a repeated k×
copies (k): 0 searches: 0

The catch: no termination on impossible input

For a b that is reachable, the loop is correct and even efficient. The problem is the -1 case: with no upper bound the loop appends a forever and times out. The insight from §1 supplies the missing rule — stop after ⌈n/m⌉+1 copies — turning this into a two-check algorithm.

int repeatedStringMatch(string a, string b) {
    string s = a;
    for (int k = 1; ; k++) {            // no upper bound!
        if (s.find(b) != string::npos) return k;
        s += a;                          // keep appending — forever if b never fits
    }
}

Step 2

Translations — every optimisation, named

Three swaps turn the unbounded naive loop into a correct constant-check algorithm.

1
Unbounded loop → bounded by ⌈n/m⌉ and +1
Only k = ⌈n/m⌉ and k + 1 can ever be the answer, so check exactly those two values and stop. This is what kills the infinite loop on impossible inputs.
guaranteed termination; at most two searches
2
Re-search the whole growing string → build once, search twice
Build s = a repeated ⌈n/m⌉ times and find(b); if absent, append one more a and find(b) again. No repeated rebuilding from scratch.
O(m + n) total instead of re-scanning every growth step
3
"Is b reachable at all?" → periodicity says −1
If b is absent from ⌈n/m⌉+1 copies it is absent from every repetition, because the tiling just repeats period m. Return -1 with confidence.
a proof of impossibility, not a guess

Step 3

The algorithm in plain English

1
Measure. Let m = |a| and n = |b|. Compute k = ⌈n/m⌉ = (n + m − 1) / m with integer division — the copies needed just to reach length n.
2
Build k copies and search. Form s = a repeated k times. If b is a substring of s, return k.
3
Try one more copy. Otherwise append a single a (now k+1 copies). If b is now a substring, return k + 1 — this is the offset case.
4
Otherwise, impossible. If neither tiling contains b, return -1. No larger repetition can help.

Step 4

Code

int repeatedStringMatch(string a, string b) {
    int m = a.size(), n = b.size();
    int k = (n + m - 1) / m;            // ceil(n / m): copies to reach length n
    string s = "";
    for (int t = 0; t < k; t++) s += a; // build k copies
    if (s.find(b) != string::npos) return k;
    s += a;                             // one extra copy covers any offset
    if (s.find(b) != string::npos) return k + 1;
    return -1;                          // b never fits → impossible
}

Step 7

Corner cases

1
b already fits in one a
a="abc", b="bc": ⌈2/3⌉ = 1, and "abc" contains "bc" → answer 1. The floor formula already returns 1 here; no special-casing needed.
2
The +1 offset case
a="abcd", b="cdabcdab": ⌈8/4⌉ = 2 copies ("abcdabcd") do not contain b because it starts at offset 2 and spills; 3 copies do → answer 3. Skipping the +1 check would wrongly report -1.
3
Impossible — character not in a
a="abc", b="abax": x never appears in any tiling of "abc", so both checks fail → -1. The bound guarantees we detect this in two searches, not an infinite loop.
4
Impossible — wrong order, right characters
a="abc", b="abac": every character of b is in a, yet "abac" never appears in "abcabcabc…" — the period-3 pattern forbids a immediately after ab. Still -1. Presence of characters is not enough.
5
Integer ceiling, not float
Compute k = (n + m − 1) / m, not ceil((double)n/m). Floating-point rounding can give the wrong copy count for large n; integer arithmetic is exact.

Step 8

Production readiness

✓
The bound is the whole point. Always cap at ⌈n/m⌉+1 copies — never an open-ended loop, or impossible inputs hang.
✓
Integer ceiling. (n + m − 1) / m avoids floating-point error on large lengths.
✓
Check both k and k+1. Returning after only the first search misses every offset case (false -1).
✓
Use a linear substring search. find can be O(m·n) worst-case in some libraries; KMP or Rabin–Karp guarantees O(m + n).
✓
Reserve the buffer. s.reserve((k + 1) * m) avoids repeated reallocation while appending copies.
✓
Mind the constraints. Both strings are non-empty per LC 686; if your context allows empty a or b, guard those before dividing by m.

Step 9

Approaches — trade-offs

O(m + n)O(m + n)

Build a repeated ⌈n/m⌉ times, search for b, append one more copy and search again, else -1. This is the intended solution: short, and with a linear substring search it is optimal. The only subtlety is the +1 bound — everything else is a direct read of the problem.

O(m + n)O(m + n)

Identical bounded build, but run the search with the Knuth–Morris–Pratt automaton so the worst case is guaranteed linear (no quadratic blow-up from a pathological find). Build b's failure function once, then scan the tiled string in a single pass.

// build s = a repeated (ceil(n/m) + 1) times, then:
vector<int> fail = buildFailure(b);   // KMP prefix function of b
int j = 0;
for (int i = 0; i < (int)s.size(); i++) {
    while (j && s[i] != b[j]) j = fail[j - 1];
    if (s[i] == b[j] && ++j == n) return copiesUpTo(i);  // match ends at i
}
O(m + n)O(1) extra

Rabin–Karp: hash b once, then roll a hash of every length-n window across the bounded tiling, comparing in O(1) per step and confirming on a hash hit. Expected linear, with the usual small collision risk; useful when you want to avoid materializing or re-scanning, but the KMP route is simpler to make worst-case safe.

Step 10

Complexity

Time
O(m + n)
Building ⌈n/m⌉+1 copies is O(n + m) characters, and one linear substring search (KMP) is O(m + n). A naive find is O(m·n) worst case — prefer a linear matcher for guarantees.
Space
O(m + n)
The repeated string s has length at most n + 2m, plus b and (for KMP) its failure array of size n.
