## Project Overview

`crack_d` is a personal, local-only web app that turns LeetCode problems into deeply intuitive, animated HTML lessons. It is a learning tool, not a tracker. The user studies a generated lesson to internalise the *intuition* behind the solution — animated dry runs, corner-case explanations, multi-approach tabs — before attempting the problem himself.

The project is built in two phases. **Phase 1 (POC)**: prove the full workflow end-to-end on 1–2 problems with zero tooling — hand-authored `plan.md`, hand-authored skill files, Claude in VS Code generates `lesson.html`, view via `python3 -m http.server`. **Phase 2 (bulk)**: parse the existing `problems/finalrepList.HTML` curated list into a JSON directory, build a vanilla HTML/JS dashboard backed by a tiny Python file-writer (`scripts/server.py`), and add the click-to-generate flow.

This project exists because grinding LeetCode without intuition is a treadmill. Animated lessons that are *consistent across problems* (same DS visual conventions, same pattern templates) compound understanding faster than ad-hoc explanations. The POC-first ordering ensures we never invest in tooling before the underlying lesson-generation workflow is proven.

### Problem Statement

Standard LeetCode prep — solving in volume — does not build the pattern-recognition and DS-intuition that a Google L5 interview demands. Existing tools track progress but don't *teach intuition*. The user needs a way to repeatedly turn problems into high-quality, visually consistent lessons without re-explaining DS conventions every time.

### Target Users

A single user — a senior software engineer preparing for a Google L5 SWE interview on the GCP team, with two DSA rounds (2 hard problems each) in ~4 weeks. The user works locally in VS Code with the Claude Pro extension and prefers offline, file-based tools over SaaS.

### Current Operational Reality (as of 2026-05-07)

Mostly greenfield with one important asset: `problems/finalrepList.HTML` — a curated 150-problem Google interview prep list, organised by topic (Arrays, Sliding Window, etc.) with LC numbers, names, links, difficulty, and per-problem done/new status. This file is the import source for the eventual `data/problems.json`. No code, no dashboard, no skill files, no lessons yet. One reference 3Sum HTML lesson exists outside the repo as the quality target.

## Architectural Principles

- **POC before tooling.** Prove the lesson-generation workflow end-to-end on one problem with zero infrastructure before building parsers, dashboards, or servers. If the manual loop produces a great lesson, the tooling is just convenience; if it doesn't, no amount of tooling will fix it.
- **Skills are reusable templates, not per-problem rewrites.** A skill file is validated only when a *second* problem uses it unchanged. Until then, treat it as a draft.
- **File-first, zero-backend.** The source of truth is files on disk: `data/problems.json`, `skills/ds/*.md`, `skills/patterns/*.md`, `lessons/<slug>/plan.md`, `lessons/<slug>/lesson.html`. No database, no real server.
- **Dashboard is a viewer + trigger, never a renderer of lessons.** Lessons are standalone HTML files; the dashboard links to them and embeds them via `<iframe>` or `window.open()`.
- **Claude is the code-gen layer, invoked by the human.** The app never calls an API. It writes a `plan.md` and a copy-paste prompt; the user runs Claude in VS Code; Claude writes the `lesson.html` back into the project.
- **Lessons are self-contained.** No shared CSS/JS bundle across lessons. Each `lesson.html` inlines what it needs so the file works if copied anywhere.
- **The localhost file-writer only writes inside the project directory.** Path traversal must be rejected. No general-purpose file API.
- **Stdlib only.** No pip installs for v1. If a need arises (e.g. faster HTML parsing), document and decide before adding.
- **Bias to ship by tomorrow EOD.** Defer everything that isn't on the v1 success-criteria list.

# FEATURE 5 — Python File-Writer Service

## Goal

A short Python script using `http.server` (stdlib only) that lets the dashboard write `plan.md` files and update `problems.json` status fields, without exposing arbitrary file write.

## Existing Code to Reference

- `data/problems.json`

## Tasks

- [ ] `scripts/server.py` using `http.server.ThreadingHTTPServer` + `BaseHTTPRequestHandler`, listening on `localhost:5173`
- [ ] CORS headers permitting `http://localhost:8000` (where the dashboard is served)
- [ ] `POST /write-plan` — body `{ slug, content }`. Writes to `lessons/<slug>/plan.md`. Reject any slug containing `/`, `..`, or non-`[a-z0-9-]` chars.
- [ ] `POST /update-status` — body `{ number, status }`. Loads `problems.json`, finds problem by number, updates status, writes back atomically (write to temp + `os.replace`).
- [ ] `GET /list-skills` — returns `{ ds: [...], patterns: [...] }` by listing the two skills dirs.
- [ ] Run instructions: `python3 scripts/server.py`. No pip install required.

## Acceptance Criteria

- [ ] `curl -X POST localhost:5173/write-plan -d '{"slug":"3sum","content":"hi"}'` writes the file
- [ ] Path-traversal attempts (`../etc/passwd`, `foo/bar`) return HTTP 400
- [ ] Killing and restarting the server has no effect on dashboard correctness as long as it's running when actions are taken
